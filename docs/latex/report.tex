\section*{摘要}
\addcontentsline{toc}{section}{摘要}

本项目面向实验室物资借还场景，设计并实现了一套分布式智能物资管理系统。系统由客户端（采集与交互）和服务端（识别与记录）组成。客户端为独立 Python 包，基于树莓派和普通 Linux 摄像头采集图像，通过 TCP 协议向服务端发送请求；服务端内部使用 ROS2 节点组织人脸识别、YOLO 物资计数、库存记录和 Web 看板，并通过多线程模型支持多个客户端并发连接。一次完整出入库操作由"人脸门控—前态拍摄—用户操作—后态拍摄—自动差分—记录写入"六步串联。当前模型在 \code{cboard}、\code{dmj4310}、\code{m3508} 三类物资上 mAP50 达到 87.74\%，mAP50-95 达到 76.15\%，能够支撑系统联调和较为简单的物资管理。

\noindent\textbf{关键词：} 嵌入式系统；物资管理；YOLO；人脸识别；TCP 协议；ROS2；库存看板；分布式系统

% ==================== 一、背景与需求 ====================
\section{背景与需求}

\subsection{问题提出}

小型实验室和机器人队伍中共享电机、电调、开发板等物资是常态。纸质表格或电子表格在借还频率低时勉强可用，但随着借用增多，三个问题逐渐突出：

\begin{enumerate}
	\item 物资被取走但忘记登记，记录与实物不符；
	\item 需要有专人进行物资的管理和定期清点，耗费人力；
	\item 记录散落在不同文件中，难以汇总查看当前库存。
\end{enumerate}

例如在如下战队的物资管理中，库中记录还有大量的C620电调，但是实际上队内已经没有能够使用的C620电调，并且该登记表由于无人管理已经多个月没有进行更新
\begin{figure}[H]
	\centering
	\includegraphics[width = 0.8\textwidth]{material_log.png}
\end{figure}


\subsection{核心需求}

系统需要满足四条核心需求：

\begin{enumerate}
	\item 操作前完成身份确认，方便对物资进行溯源；
	\item 尽量实现自动化，减少队员出入库物资的操作；
	\item 客户端保持轻量，能在树莓派等轻量化普通 Linux 环境中直接运行；
	\item 服务端记录每次出入库流水，并提供本地看板便于检查。
\end{enumerate}

围绕这些需求，系统按"客户端采集—网络通信—服务端识别—记录展示"四层划分。客户端负责摄像头预览和用户交互，服务端负责推理、记录和展示，两层之间通过 TCP 长连接通信。

\subsection{总体架构}

\begin{figure}[H]
	\centering
	\includegraphics[width=0.95\textwidth]{system_architecture_gpt_image2}
	\caption{系统总体架构}
	\label{fig:system-arch}

客户端与服务端的边界很明确：客户端只做采集和交互，通过 TCP 发送 \code{face\_image}、\code{material\_image}、\code{inventory\_record} 三类请求；服务端收到图片类请求后转成 ROS2 \code{Image} 消息发布到识别节点，识别结果以 JSON 返回；库存请求经校验后直接追加到 CSV 文件。Web 看板节点周期性读取同一份 CSV，构建当前库存、最近事件和低库存提示。

这种结构把压力分布在合适的位置：树莓派只做采集和交互，服务器负责推理和汇总；客户端只需要轻量化的python环境，服务端利用ROS2 对多个模块进行良好地组织。

\subsection{主流程设计}

一次出入库操作的主流程如图~\ref{fig:workflow} 所示，核心设计是"先身份、再前态、再后态、最后差分"。

\begin{figure}[H]
	\centering
	\includegraphics[width=0.65\textwidth]{project_workflow_gpt_image2}
	\caption{出入库主流程}
	\label{fig:workflow}
\end{figure}

客户端初始状态为 \code{idle}。用户点击 Start 后进入 \code{recognizing\_face}，程序每隔约 1 秒抓拍人脸图发往服务端。只有当服务端返回 \code{total\_faces=1} 且唯一人脸不是 \code{unknown} 时，才记录操作者姓名并进入 \code{waiting\_camera\_move}。识别通过后，用户将摄像头对准物资区域，点击 \code{Capture Materials} 拍摄前态图像。用户完成实际借还操作后点击 Finish，客户端拍摄后态图像。两次 \code{material\_image} 返回后，\code{compute\_inventory\_changes()} 对两份计数字典逐项求差——正差生成入库条目，负差生成出库条目；若差分为空，流程直接结束，不写入无意义流水。

前态拍摄采用手动触发而非自动判断，是因为早期尝试通过画面稳定性自动触发，但当前系统只有一个摄像头，在移动摄像头和现场遮挡场景下误拍率较高，改为手动确认后流程更可控。

% ==================== 三、关键技术实现 ====================
\section{关键技术实现}

\subsection{客户端：轻量化与状态机}

\begin{enumerate}
	\item \textbf{仿ROS2的代码结构。}为保证客户端部署的轻量化，客户端未使用ROS2，但采用与ROS2类似的组织结构，分出logic\_node,capture\_node,ui\_node,tcp\_node,将不同的功能写在不同的节点中，最后再全部组织起来

	\item \textbf{相机采集原理。} 摄像头通过连续抓取视频帧为 UI 预览提供流式画面，同时支持在业务请求时捕获当前帧作为识别输入。由于客户端部署在树莓派上，且相机使用排针相机，因此相机后端采用自动选择策略：若环境中有 \code{rpicam-still}，通过命令行输出 JPEG 到标准输出并在内存中解码；否则回退到 OpenCV。选择 \code{rpicam-still} 的原因是树莓派新系统中它比直接打开 OpenCV 摄像头更稳定，回退路径保证普通 USB 摄像头也能用于开发调试。

	\item \textbf{有限状态机原理。} 有限状态机（Finite State Machine, FSM）将系统行为拆为有限个状态，每个状态只允许特定的输入和状态转移。在本系统中，出入库操作天然具有顺序性——必须先完成身份认证才能拍摄物资、必须先拍前态才能拍后态——FSM 正好保证用户不能跳步执行。

	\item \textbf{具体实现。} 流程控制基于 FSM，\code{LogicNode} 在 \code{client/client/logic\_node.py} 中实现，关键状态共 7 个：\code{recognizing\_face}、\code{waiting\_camera\_move}、\code{capturing\_pre\_material}、\code{waiting\_finish}、\code{capturing\_post\_material}、\code{computing\_diff} 和 \code{submitting\_inventory}。每个状态只开放当前合理的操作：\code{recognizing\_face} 状态仅允许 Start 按钮可用、\code{waiting\_camera\_move} 状态仅允许 Capture Materials 可用、\code{waiting\_finish} 状态仅允许 Finish 可用。UI 层不关心识别细节，只通过三个按钮将用户意图交给 \code{LogicNode}：

	      \begin{lstlisting}[caption={客户端状态机核心入口},label={lst:logic-state}]
def start_operation():
    reset workflow data
    state = "recognizing_face"

def capture_material_now():
    require state == "waiting_camera_move"
    capture material snapshot as "pre"

def finish_operation():
    require state == "waiting_finish"
    record finish time
    capture material snapshot as "post"
\end{lstlisting}

	\item \textbf{库存差分原理。} 差分计算的核心思想是：操作前计为基准 $P$，操作后计为 $Q$，对于每个物资类别 $i$，变化量 $\Delta_i = Q_i - P_i$。$\Delta_i > 0$ 时入库 $|\Delta_i|$ 件，$\Delta_i < 0$ 时出库 $|\Delta_i|$ 件，$\Delta_i = 0$ 时不产生记录。该逻辑在 \code{client/client/logic\_utils.py} 中实现：

	      \begin{lstlisting}[caption={库存差分逻辑},label={lst:inventory-diff}]
for name in sorted(set(pre_counts) | set(post_counts)):
    pre_value = int(pre_counts.get(name, 0))
    post_value = int(post_counts.get(name, 0))
    delta = post_value - pre_value
    if delta > 0:
        added_items.append({"name": name, "quantity": delta})
    elif delta < 0:
        removed_items.append({"name": name, "quantity": -delta})
\end{lstlisting}
\end{enumerate}

\subsection{TCP 协议与跨设备通信}

\begin{enumerate}
	\item \textbf{协议设计原理。} TCP 是面向连接的可靠字节流协议，保证数据按序、无差错到达，但 TCP 本身不提供消息边界——"一次 send"不一定对应"一次 recv"。因此应用层必须自定义分帧机制。常见的方案有三种：(1) 固定长度消息；(2) 分隔符（如换行符）；(3) 长度前缀。本系统选择方案 (3)，因为图片数据可能包含任意字节序列，分隔符不可靠；固定长度对大小不一的图像请求不适用。

	\item \textbf{双长度前缀格式。} 每条消息格式为"4 字节 JSON 长度（大端）+ 4 字节附件长度（大端）+ UTF-8 JSON 头 + 可选二进制图像体"。收端先读 8 字节固定头得到两段长度，再按长度分别读取 JSON 和附件。JSON 头无换行符、保持紧凑，图像体作为独立二进制附件发送，不再将图片 \code{base64} 嵌入 JSON。

	\item \textbf{帧头编解码实现。} 双长度前缀由 \code{struct.Struct("!II")} 打包和解包，\code{!} 表示大端字节序，\code{II} 表示两个无符号 32 位整数。收端的 \code{recv\_exactly()} 循环读取直到收满指定字节数，以此防御 TCP 分包：

	      \begin{lstlisting}[caption={TCP 消息收发（两端共用的 \code{tcp\_protocol.py}）},label={lst:tcp-protocol}]
MESSAGE_PREFIX = struct.Struct("!II")

def recv_exactly(sock, size):
    chunks = bytearray()
    while len(chunks) < size:
        data = sock.recv(size - len(chunks))
        if not data:
            raise ConnectionClosedError("Peer closed the connection")
        chunks.extend(data)
    return bytes(chunks)

def receive_message(sock):
    header = recv_exactly(sock, MESSAGE_PREFIX.size)
    json_len, attachment_len = MESSAGE_PREFIX.unpack(header)
    body = recv_exactly(sock, json_len)
    attachment = recv_exactly(sock, attachment_len) if attachment_len else b""
    payload = json.loads(body.decode("utf-8"))
    return payload, attachment

def send_message(sock, payload, attachment=b""):
    encoded = json.dumps(payload, ensure_ascii=False).encode("utf-8")
    sock.sendall(MESSAGE_PREFIX.pack(len(encoded), len(attachment))
                 + encoded + attachment)
\end{lstlisting}

	\item \textbf{请求分发。} 得益于校园网的存在，server端和client端只需要在同一个校网环境下即可进行tcp通信，不需要在同一个地点。服务端支持三类请求，\code{TcpBridgeNode} 根据 \code{type} 字段分发：

	      \begin{lstlisting}[caption={TCP 网桥分发逻辑},label={lst:tcp-bridge-dispatch}]
if request_type == "material_image":
    image = decode_image_payload(payload, attachment)
    return submit_image_request(material_publisher, request_id, image)

if request_type == "face_image":
    image = decode_image_payload(payload, attachment)
    return submit_image_request(face_publisher, request_id, image)

if request_type == "inventory_record":
    record = validate_inventory_payload(payload)
    data = write_inventory_record(request_id, record)
    return make_success_response("inventory_record_result", request_id, data)
\end{lstlisting}

	\item \textbf{传输优化。} 统计数据显示，相比旧版 \code{base64 + jpeg} 方案，新协议在 13 张测试样本（11 张物资图 + 2 张人脸图）上，平均 TCP 报文从 2.47 MB 降至 0.37 MB，降幅 84.53\%。
\end{enumerate}

\subsection{服务端：分布式多客户端并发}

\begin{enumerate}
	\item \textbf{并发模型原理。} 服务端需要同时处理来自多个树莓派客户端的请求。常见的并发模型有三种：(1) 单线程轮询（\code{select/poll}），适合 IO 密集型场景，但需要手动维护状态机；(2) 线程池模型，主线程 accept 后将连接交给线程池中的工作线程，适合请求耗时较均匀的场景；(3) 一线程一连接模型，每个 TCP 连接分配一个独立线程，连接间天然隔离，编程模型简单。本系统选择方案 (3)，因为课程项目阶段客户端数量有限（$< 10$ 个），且每个连接的识别请求耗时主要由远端模型推理决定，线程间隔离可以避免某个慢请求阻塞其他客户端。

	\item \textbf{多线程 TCP 接收循环。} 主线程在端口上执行 \code{accept()} 阻塞等待新连接。每当新客户端接入，\code{TcpBridgeNode} 创建一个守护线程运行 \code{\_client\_loop()}，该线程内循环接收消息、处理请求并返回响应。\code{MultiThreadedExecutor} 确保 ROS2 回调在多线程环境下安全执行：

	      \begin{lstlisting}[caption={服务端多线程 TCP 接收模型},label={lst:tcp-server-model}]
class TcpBridgeNode(Node):
    def __init__(self):
        # ... ROS2 发布/订阅初始化 ...
        self._server_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        self._server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        self._server_socket.bind((self.host, self.port))
        self._server_socket.listen()
        self._accept_thread = threading.Thread(
            target=self._accept_loop, name="tcp-bridge-accept", daemon=True
        )
        self._accept_thread.start()

    def _accept_loop(self):
        while not self._stop_event.is_set():
            client_socket, address = self._server_socket.accept()
            thread = threading.Thread(
                target=self._client_loop,
                args=(client_socket, address),
                daemon=True,
            )
            self._client_sockets.add(client_socket)
            self._client_threads.add(thread)
            thread.start()

    def _client_loop(self, client_socket, address):
        while not self._stop_event.is_set():
            request, attachment = receive_message(client_socket)
            response = self._handle_request(request, request_id, attachment)
            send_json_message(client_socket, response)
\end{lstlisting}

	\item \textbf{连接管理与健康监控。} 为防止资源耗尽，系统实现了三个关键机制：(1) 连接上限控制——新增 \code{max\_connections} 参数（默认 10），accept 时检查当前连接数，超出则拒绝新连接并关闭 socket；(2) 每连接统计跟踪——使用 \code{ClientSession} 数据类记录每个连接的建立时间、请求次数、收发字节量和最后活跃时间；(3) 定时健康报告——每 30 秒输出一次连接总览日志，便于运维排查：

	      \begin{lstlisting}[caption={连接管理与会话跟踪},label={lst:connection-mgmt}]
@dataclass
class ClientSession:
    address: tuple[str, int]
    connected_at: float
    request_count: int = 0
    error_count: int = 0
    bytes_received: int = 0
    bytes_sent: int = 0
    last_active: float = field(default_factory=time.monotonic)

def _accept_loop(self):
    while not self._stop_event.is_set():
        client_socket, address = self._server_socket.accept()
        if self.max_connections > 0:
            with self._session_lock:
                active = len(self._sessions)
            if active >= self.max_connections:
                self.get_logger().warn(
                    f"Rejected {address} — {active}/{self.max_connections} full"
                )
                client_socket.close()
                continue
        # ... 创建 ClientSession，启动 _client_loop 线程 ...

def _log_health_report(self):
    """每隔 30 秒输出连接总览"""
    with self._session_lock:
        sessions = list(self._sessions.items())
    for peer, session in sessions:
        conn_sec = time.monotonic() - session.connected_at
        logger.info(
            f"  {peer}  id={conn_sec:.0f}s  req={session.request_count}  "
            f"err={session.error_count}  rx={session.bytes_received}B"
        )
\end{lstlisting}

	\item \textbf{优雅关闭。} 节点销毁时按以下顺序清理资源：设置停止标志 $\to$ 关闭监听 socket $\to$ 依次 shutdown 所有客户端 socket $\to$ 等待 accept 线程退出 $\to$ 等待所有 client\_loop 线程退出 $\to$ 清理待处理请求并返回 \code{SHUTDOWN} 错误码。这种顺序保证已建立连接能正常收到关闭通知，而非被粗暴断开。
\end{enumerate}

\subsection{ROS2 节点化识别}

\begin{enumerate}
	\item \textbf{节点模型原理。} ROS2 的节点模型将功能拆为独立进程或线程，节点之间通过 topic（发布/订阅）、service（请求/响应）或 action（带反馈的长时间任务）交换消息。发布者和订阅者只依赖消息类型，不直接依赖彼此实现，天然支持模块替换。

	\item \textbf{服务端节点划分。} 服务端保留 ROS2 Humble 包结构，核心 launch 文件 \code{tcp\_bridge.launch.py} 同时启动四个节点：物资识别节点、人脸识别节点、TCP 网桥和 Web 看板。TCP 网桥将外部请求转为 ROS2 图像消息，识别节点订阅图像并发布 JSON 结果。拆分的主要收益有两点：一是服务端硬件资源比客户端宽裕，适合集中安装模型库和人脸识别依赖；二是节点化降低单个文件维护压力——旧版 \code{integrated\_server.py} 725 行，当前最大服务端节点 \code{tcp\_bridge\_node.py} 约 410 行，人脸节点 \code{face\_recognize\_node.py} 99 行。

	\item \textbf{请求关联机制。} 网桥与识别节点之间通过 \code{request\_id} 关联异步响应：网桥将 \code{request\_id} 写入 \code{Image.header.frame\_id}，识别节点返回结果时保留同一 \code{frame\_id}，网桥据此在等待表（\code{\_pending} 字典）中找到对应的 TCP 请求并返回结果。超时保护由 \code{threading.Event.wait(timeout)} 实现，默认 15 秒。

	      \begin{lstlisting}[caption={网桥请求等待与结果回调},label={lst:ros2-bridge}]
def _submit_image_request(self, publisher, request_id, image, response_type):
    pending = PendingResponse(event=threading.Event())
    self._pending[request_id] = pending
    msg = bgr_to_image_msg(image, frame_id=request_id)
    publisher.publish(msg)
    if not pending.event.wait(self.request_timeout_sec):
        raise ProtocolError("TIMEOUT", f"Timed out waiting for {response_type}")
    return pending.response

def _complete_pending_from_result(self, payload_text, response_type):
    payload = json.loads(payload_text)
    request_id = payload.get("frame_id")
    pending = self._pending.get(request_id)
    if pending is not None:
        pending.response = make_success_response(response_type, request_id, payload)
        pending.event.set()
\end{lstlisting}
\end{enumerate}

\subsection{物资检测}

\begin{enumerate}
	\item \textbf{YOLO 单阶段检测原理。} YOLO（You Only Look Once）将目标检测建模为回归问题：将输入图像划分为 $S \times S$ 的网格，每个网格预测 $B$ 个边界框及对应的置信度 $C$ 和类别概率 $P(\text{class})$。最终输出直接来自一次前向推理，没有候选区域生成（RPN）阶段。模型输出经过非极大值抑制（NMS）去除冗余框后，得到最终检测结果。

	\item \textbf{计数转换。} 物资识别节点在 \code{server/server/material\_counter\_node.py} 中实现，订阅 \code{/material\_counter/image} 话题，在 \code{image\_callback()} 中调用 \code{model.predict()} 进行推理。检测结果通过 \code{summarize\_counts()} 按类别累加检测框数量，返回类似 \code{\{"cboard": 2, "m3508": 1\}} 的计数字典。节点默认通过 \code{resolve\_default\_model\_path()} 查找权重，优先使用 \code{last.pt}，找不到时回退到 \code{best.pt}。相比早期方案中的二维码逐件扫描，YOLO 差分方式只需拍前后两张图，不需要为每件物资制作和维护标签。

	      \begin{lstlisting}[caption={物资检测节点回调逻辑（\code{material\_counter\_node.py}）},label={lst:material-counter}]
def image_callback(self, msg):
    image = image_msg_to_bgr(msg)
    predictions = self.model.predict(
        source=image, conf=self.conf_threshold,
        device=self.device, verbose=False,
    )
    result = predictions[0]
    counts = summarize_counts(result)
    payload = {
        "frame_id": msg.header.frame_id,
        "counts": counts,
        "total_detections": int(sum(counts.values())),
    }
    self.counts_publisher.publish(
        String(data=json.dumps(payload, ensure_ascii=False)))
\end{lstlisting}
\end{enumerate}

\subsection{人脸识别门控}

\begin{enumerate}
	\item \textbf{人脸编码比对原理。} \code{face\_recognition} 库基于 dlib 的深度学习模型，将人脸图像映射为 128 维特征向量（face encoding）。同一人的不同照片在编码空间中距离较近（欧氏距离通常 $< 0.6$），不同人的编码距离明显更大。识别过程分三步：(1) 用 HOG（Histogram of Oriented Gradients）或 CNN 检测人脸位置；(2) 将检测到的人脸区域输入编码网络得到 128 维向量；(3) 计算待识别人脸编码与库中已知编码的欧氏距离，取最小距离者，若低于阈值则匹配。已知人脸库由 \code{server/server/face\_database.py} 中的 \code{load\_known\_face\_database()} 从磁盘加载并预编码。

	\item \textbf{门控规则。} \code{FaceRecognizeNode} 在 \code{server/server/face\_recognize\_node.py} 中实现，订阅 \code{/face\_recognize/image} 话题，在 \code{image\_callback()} 中调用 \code{recognize\_faces()} 进行编码比对，返回识别结果、计数字典和总人脸数。客户端只有在服务端返回 \code{total\_faces=1} 且唯一姓名不是 \code{unknown} 时才继续。这条规则可以过滤三种不可靠场景：(1) 画面中无人——可能是摄像头未对准；(2) 画面中有多人——无法确定操作者；(3) 画面中的人不在已知库中——无权限。后续 CSV 中的每条记录都带有操作者姓名，追溯时不需要再反推"这次是谁登记的"。

	      \begin{lstlisting}[caption={人脸识别节点回调逻辑（\code{face\_recognize\_node.py}）},label={lst:face-recognize}]
def image_callback(self, msg):
    image = image_msg_to_bgr(msg)
    results = recognize_faces(
        image, self.known_encodings, self.known_names,
        tolerance=self.tolerance,
        detection_model=self.detection_model,
        unknown_label=self.unknown_label,
    )
    counts = dict(sorted(Counter(
        str(item["name"]) for item in results).items()))
    payload = {
        "frame_id": msg.header.frame_id,
        "results": results,
        "counts": counts,
        "total_faces": len(results),
    }
    self.result_publisher.publish(
        String(data=json.dumps(payload, ensure_ascii=False)))
\end{lstlisting}
\end{enumerate}

\subsection{库存记录与看板}

\begin{enumerate}
	\item \textbf{记录原理。} 库存记录将一次差分结果拆为多条追加式流水，每行包含 \code{request\_id}、\code{record\_time}、\code{person}、\code{action}（"入库"或"出库"）、\code{material\_name}、\code{quantity} 和 \code{received\_at}。\code{TcpBridgeNode} 的 \code{\_write\_inventory\_record()} 方法负责将校验后的库存流水追加到 CSV 文件，使用 \code{\_csv\_lock} 线程锁保护文件写入，防止多客户端并发写入导致数据交错：

	      \begin{lstlisting}[caption={CSV 库存记录写入（\code{tcp\_bridge\_node.py}）},label={lst:csv-write}]
def _write_inventory_record(self, request_id, record):
    rows = [{
        "request_id": request_id,
        "record_time": record.record_time,
        "person": record.person,
        "action": record.action,
        "material_name": item.name,
        "quantity": item.quantity,
        "received_at": datetime.now().astimezone().isoformat(),
    } for item in record.items]
    self.inventory_csv_path.parent.mkdir(parents=True, exist_ok=True)
    with self._csv_lock:
        write_header = (not self.inventory_csv_path.exists()
                        or self.inventory_csv_path.stat().st_size == 0)
        with self.inventory_csv_path.open("a", newline="", encoding="utf-8") as f:
            writer = csv.DictWriter(f, fieldnames=CSV_FIELDNAMES)
            if write_header:
                writer.writeheader()
            writer.writerows(rows)
    return {"csv_path": str(self.inventory_csv_path), "rows_written": len(rows)}
\end{lstlisting}

	\item \textbf{看板原理。} Web 看板基于 Python 标准库 \code{http.server} 和 \code{ThreadingHTTPServer}，默认监听 \code{127.0.0.1:8600}。\code{DashboardStore} 定时读取 CSV，通过 \code{server/server/inventory\_dashboard.py} 中的 \code{build\_dashboard\_data()} 逐行解析流水记录，按物资名称聚合当前库存、累计入库/出库量、交易次数和最后操作者，并根据 \code{get\_stock\_status()} 判定库存状态（待补货/偏低/平稳/充足）。前端收到 \code{/api/summary} 后渲染库存总览表和最近动态，并通过 SSE（Server-Sent Events）推送增量更新。看板让演示时不必打开代码或 CSV 就能确认系统是否完成了记录闭环。
\end{enumerate}

% ==================== 六、系统评估 ====================
\section{系统评估}

\subsection{系统特点}

\textbf{1. ros2组织代码。} 

\textbf{2. 单样本的人脸识别。} 

\textbf{3. 客户端轻量化。} 

\textbf{4. 多客户端并发处理。} 服务端 TCP 网桥采用一线程一连接模型，主线程 \code{accept} 后将连接交给独立守护线程，各连接之间互不干扰。配合连接上限、会话统计和定时健康报告，系统具备基本的分布式部署能力——多个实验室门禁点的树莓派可以同时接入同一服务端。

\textbf{5. tcp无线通信} 减少了部署的空间难度

\subsection{不足与改进方向}

项目大体可以运行，但仍有改进空间：

\begin{enumerate}
	\item 物资检测目前只覆盖三类目标，数据集 61 张偏小。后续应扩充样本，补充强反光、遮挡、相似背景和密集摆放场景；
	\item 人脸库成员较少，光照和姿态变化需要更充分测试；
	\item CSV 存储不适合长期使用，多人长期使用应迁移到如sql之类的数据库，并补充权限控制和异常审核；
	\item 当前只有一个摄像头，权衡之下物资拍摄仍需手动触发，后续可使用两个摄像头，一个用于人脸拍摄，一个用于物资拍摄
	\item 当前一线程一连接模型在客户端数量 $> 50$ 时线程开销较大，未来可考虑改用 \code{asyncio} 或线程池模型。
\end{enumerate}

本项目完成了一套从图像采集到库存展示的分布式智能物资管理系统。系统的价值体现在将 YOLO 识别、人脸门控、TCP 通信、多线程并发、库存差分、CSV 落盘和 Web 看板串联为一个完整闭环。当前实现证明了"轻量客户端 + 集中式服务端 + 本地可视化看板"的路线在课程项目阶段具有可行性。系统的模块化结构和清晰的接口边界为后续扩展更多物资类别、数据库存储和更自动化的端侧交互预留了空间。
